## 项目背景

这个项目是为学习而做的：**以 MySQL 为参照，系统性地学习数据库内核**。数据库是后端技术的集大成者——SQL 解析（编译原理）、查询优化（代价模型）、存储引擎（数据结构与磁盘 IO）、事务（并发控制与崩溃恢复）、网络接入（高并发服务端编程），每一项都是后端开发的核心基础。与其零散地看博客，不如从零手写一个，把"一条 SQL 从输入到返回结果"的每个环节真正跑通。

技术选型上用了 C++17 + CMake，不依赖任何第三方库（词法/语法解析器、B+Tree、WAL、epoll 网络层全部手写；唯一的"外部"组件是配套的 Qt6 图形客户端，用 QTcpSocket 走自定义协议访问服务端）。原因有二：

1. 用现成的库/框架会把底层细节藏起来（比如用 yacc 生成解析器、直接套 SQLite），学不到内核层面的东西；
2. 数据库性能敏感，C++ 最贴近系统，RAII 与智能指针也能管住系统软件的资源复杂度。

项目目标定得很务实：**不追求功能大而全，而是把一条完整的链路做深**——从客户端输入 SQL、词法/语法解析、语义检查、查询优化、火山模型执行、文件落盘，到 WAL 崩溃恢复与事务并发控制，端到端全部打通。

## 总体架构

整体采用**分层架构 + 一次一行的执行流水线**：

```
客户端层：Qt6 GUI（QTcpSocket 异步收发，信号槽驱动 UI）
    │  自定义文本协议（SQL + txnId → success + columns + rows）
    ▼
网络层：Reactor（epoll 事件循环）
    ├─ EPOLLONESHOT：同一连接同一时刻只被一个工作线程处理
    └─ ThreadPool（固定线程数，packaged_task + future）
    ▼
解析层：Lexer（逐字符扫描生成 Token，带行列定位）
    ├─ Parser（递归下降生成 AST，表达式优先级分层函数）
    └─ SemanticAnalyzer（表/列存在性、类型检查、GROUP BY 合法性）
    ▼
优化层：QueryRewriter（谓词下推 / 常量折叠）
    ├─ RuleOptimizer + CostOptimizer（统计信息 + 代价估算）
    ├─ IndexSelector（选择性计算、覆盖索引识别）
    └─ PlanGenerator（生成物理算子树）
    ▼
执行层：火山模型（open / next / close 迭代器协议）
    ├─ TableScan / Filter / Project / NLJ / Sort / Limit / Aggregate / SubqueryScan
    └─ ExpressionEvaluator（表达式树后序求值）
    ▼
存储层：TableManager（.data / .meta / .rowid 文件）
    ├─ BPlusTree（阶数 200，叶子链表，序列化到 .idx）
    └─ IndexManager（主键索引 + 普通索引）

横切：TransactionManager（thread_local 绑定事务）
    ├─ WALManager（LSN + BEGIN/INSERT/UPDATE/DELETE/COMMIT + force flush）
    └─ LockManager（表级读写锁 + 5 秒超时）
```

一次请求的数据流（以 SELECT 为例）：

```
客户端发送 SQL → epoll 可读事件 → 提交线程池
  → Lexer 生成 Token 流 → Parser 递归下降生成 AST
  → 语义分析检查合法性 → 优化器四阶段产出物理算子树
  → 执行引擎 open() 初始化 → 循环 next() 逐行拉取（上层算子驱动下层）
  → 结果集序列化 → 写回 socket → Qt 客户端渲染表格
```

值得单独说的是执行引擎的设计：**算子即迭代器**。所有算子统一实现 `open() / next() / close()` 三个接口，`next()` 返回 `Result<std::optional<Tuple>>`——一个返回类型同时表达"错误 / 有数据 / 没数据"三种状态；算子树本身就是执行计划，上层算子拉取下层输出，数据像流水线一样逐行流过，全链路内存占用 O(1) 行。

## 关键技术决策

**1. 手写递归下降 vs yacc/bison 生成**

经典的选择题：用解析器生成器还是手写？生成器能少写代码，但生成的代码不可读、错误信息不友好、调试困难。手写递归下降让每个语法规则对应一个函数，报错能精确到行列，还方便扩展新语法（子查询、EXPLAIN 都是后续加的）。表达式优先级用经典的分层函数解决，每层只消费自己的运算符：

```cpp
// Parser.cpp：优先级从低到高逐层下钻
parseExpression(OR) → parseAndExpression(AND) → parseComparison(==, !=, <, >)
  → parseAdditive(+, -) → parseMultiplicative(*, /) → parsePrimary(字面量/列名/括号)
```

代价是手写量大（Parser.cpp 约 1400 行），且要规避左递归——分层函数天然规避。PostgreSQL 等工业级数据库也是手写递归下降，这个选型经得起推敲。

**2. 火山模型 vs 物化执行**

执行引擎选了火山模型（一次一行）：统一迭代器接口让算子自由组合、每个算子可独立单测、全链路内存 O(1)。代价是每行都走一次虚函数调用，CPU 缓存不友好、无法 SIMD 向量化——业界正是因此从火山模型演进到向量化执行（ClickHouse/DuckDB），这是已知的优化方向，属于"正确性优先"的取舍。

**3. 查询优化器：把"选索引"变成可解释的决策**

很多课程数据库是"WHERE 里有索引列就走索引"的拍脑袋策略。我实现了四阶段优化流水线：查询重写（谓词下推、常量折叠）→ 规则优化 → 代价优化 → 计划生成。其中 IndexSelector 会解析 WHERE 条件，计算每个索引的**选择性**（满足条件的行占比，越小过滤效果越强），并识别等值条件与**覆盖索引**，让"走索引还是全表扫"有据可依；配套 EXPLAIN 输出执行计划（表格/JSON 两种格式），查询性能可解释、可调优。

**4. B+Tree 索引：为磁盘设计的数据结构**

为什么不是红黑树/哈希？红黑树树高 log₂N，每向下一层就是一次磁盘随机 IO，大表撑不住；哈希等值查询 O(1) 但不能范围查询、不能排序。B+Tree 阶数 200 时，100 万行数据树高仅约 3 层（查询 IO 次数 = 树高）；数据全在叶子节点、叶子间有链表，范围查询先二分找下界、再顺序遍历。建表时自动为主键建 PRIMARY 索引，DML 时同步维护。

诚实的边界：当前索引是**内存常驻 + 整树序列化**到 .idx 文件，不是工业级的页式存储（详见踩坑 1）。

**5. WAL：先写日志，再写数据**

直接写数据文件，写一半崩溃就会留下一堆不确定状态。WAL 让所有修改先**顺序追加**到日志（顺序 IO 远快于随机 IO），数据文件延迟落盘；崩溃恢复时靠日志判断哪些事务该重做、哪些该撤销。实现上每条日志带事务 ID、操作类型、键值、LSN（单调递增）；commit 时写 COMMIT 记录并 force flush，保证"日志先于数据"落盘——这是持久性与原子性的地基。

**6. Reactor + 线程池 vs 每连接一线程**

每连接一线程在 C10K 场景下线程数爆炸、上下文切换开销巨大。Reactor 让一个 epoll 事件循环管理所有连接，读事件到来后把任务提交线程池处理；用 EPOLLONESHOT 保证同一连接同一时刻只被一个工作线程处理，避免多线程并发读写同一 socket。线程池用互斥锁 + 条件变量 + `std::packaged_task` 实现，submit 返回 `std::future` 可拿处理结果。这是 Nginx、Redis 等高性能服务的共同思路。

**7. 事务：线程绑定 + 表级锁 + 逆序撤销**

事务与线程绑定（`thread_local`），每个线程有自己的当前事务，天然支持多线程并发；锁管理器维护表级读写锁（读读共享、读写互斥）+ 5 秒超时（超时即放弃，简单应对死锁）；回滚靠事务内记录的操作日志（类型、表、键、旧值、新值）**逆序撤销**——后做的操作先撤销，像一个撤销栈。三件套合起来构成基础事务闭环：WAL 保证持久性、锁保证隔离性、逆序撤销 + WAL 保证原子性。

## 踩坑记录

### 踩坑 1：索引"磁盘化"名不副实

**现象**：复盘时发现索引文件（.idx）实际是整棵 B+Tree 的序列化文本，启动时整树加载进内存——"磁盘索引"的说法并不严谨。

**排查**：查看 IndexManager::saveIndex 的实现，`tree->serialize()` 把整棵树一次性序列化写入文件，反序列化时整树重建。这意味着索引大小受内存限制，数据量上来后启动加载也会变慢。

**根因**：先做"功能正确"再做"工程完备"——内存实现逻辑最简单，整树序列化只是持久化的最小可用方案，而不是真正的磁盘数据结构。

**修复方向**：页式存储——每个节点映射一个磁盘页（4K/8K/16K），Buffer Pool 做页缓存 + LRU 淘汰，只有被访问的页才换入内存，脏页延迟写回并配合 WAL 保证崩溃一致。这是工业级数据库的标准做法，也是我明确的下一步。

### 踩坑 2：WAL 有框架、没有恢复

**现象**：WAL 的写入、LSN 分配、flush 都完成了，但崩溃恢复的 redo 回放是空实现——recover() 只解析日志、随后直接清空，代码里标着 `TODO: 实现完整的恢复逻辑`。

**排查**：梳理恢复流程时发现，日志解析后没有"按 LSN 重放已 COMMIT 事务"这一步，事务管理器初始化时调用 recover() 后直接 truncate 日志。

**根因**：先把写路径做通了（写日志、提交），读路径（崩溃恢复）优先级排后，留下了半截逻辑。

**修复方向**：按 LSN 顺序重放所有已 COMMIT 事务的日志，跳过未提交事务；定期打检查点（checkpoint）截断日志、缩短恢复时间。

### 踩坑 3：事务模块与 SQL 层脱节

**现象**：TransactionManager / LockManager / WAL 三个模块独立搭建且各有单测，但 Parser 里没有 BEGIN/COMMIT/ROLLBACK 语法，DMLExecutor 也不调用 recordOperation——SQL 层实际是逐条自动提交模式。

**排查**：全局搜索 BEGIN/COMMIT 关键字，只出现在事务模块内部；SQL 执行路径（解析 → 分发 → 执行）完全没有事务的入口和包裹。

**根因**：自底向上开发——先做底层模块（事务、锁、WAL），端到端接线（语法接入 + 执行器分发 + 事务包裹）留到最后，还没做完就收尾了。

**修复方向**：Parser 加三个关键字 → Executor 分发到 TransactionManager → DML 执行前 recordOperation、事务内自动加表锁 → 显式事务（BEGIN…COMMIT）与自动提交模式共存。

### 踩坑 4：协议假设"一次 recv 拿完整消息"

**现象**：SQL 较长或网络分片时，服务端可能收到不完整的请求；多条请求连发时又可能一次收到多条（粘包）。

**排查**：TcpConnection 的读处理按"一次 recv 即一条消息"处理，没有应用层接收缓冲与拆包逻辑。

**根因**：TCP 是字节流、没有消息边界，正确做法是应用层协议自己划分边界；当时为了快速打通全链路跳过了这一步。

**修复方向**：每个连接维护独立的读缓冲区，协议加长度字段：先读包头拿消息长度，缓冲区不足就等下次数据到达续读，够了再按长度切出完整消息（"长度字段 + 包头"是业界主流，Redis RESP 的分隔符是另一流派）。

## 性能与效果

系统压测数据待补充（插入吞吐、索引 vs 全表扫描对比、并发 QPS），以下是设计层面的复杂度结论：

| 场景 | 复杂度 | 说明 |
|---|---|---|
| 主键等值查询 | O(logₘN) ≈ 3 次访问 | 阶数 200，100 万行树高约 3 层，节点内二分 |
| 范围查询 | O(logₘN + K) | 叶子链表顺序遍历 K 个结果，无需回溯 |
| 全表扫描 | O(N) | TableScan 全表加载内存后逐行过滤 |
| JOIN | O(N×M) | 嵌套循环连接；大表应换 Hash Join / Sort-Merge Join |
| 排序 | O(N log N) | Sort 算子全量收集后排序（阻塞算子） |

与 MySQL 对比：

- **机制层面**：解析 → 优化 → 执行 → 存储的分层流水线、B+Tree 索引、WAL 事务、epoll 网络接入，与 MySQL 架构同源；
- **工程层面**：差距明显——MySQL 有 Buffer Pool、MVCC + 行级锁、完整的 redo/undo 恢复、基于统计信息的代价模型、哈希连接与并行执行。

已知局限（都有明确改进方案）：表级锁并发度低（→ 行级锁 + MVCC）；JOIN 只有嵌套循环（→ Hash Join）；B+Tree 内存常驻（→ 页式 + Buffer Pool）；WAL 恢复未实现；协议无拆包；TableScan 全表加载内存（→ 分页读取）。

## 复盘与收获

**1. 对数据库的理解从"会用"变成"能造"**

以前知道"SQL 会经过解析器和优化器"，做完之后能说清每一步为什么：为什么递归下降适合手写（每个语法规则一个函数、错误可控、可扩展）、为什么执行计划是一棵算子树（算子即迭代器、可任意组合）、为什么 B+Tree 是磁盘之王（树高 = IO 次数）、为什么先写日志再写数据（顺序 IO 换崩溃安全）。

**2. 火山模型让我真正理解了"迭代器即执行计划"**

执行引擎不是一段顺序执行的代码，而是一棵可以任意组合的算子树；上层算子拉取下层输出，像一个管道系统。这也让我理解了优化器为什么能发挥作用——它调整的正是这棵树的形状：谓词下推就是给树"整形"，把过滤往下沉，join 前的中间结果就越小。

**3. 排障方法论：状态机完备性 + 单测隔离**

事务、锁、解析器、B+Tree 都是状态密集的模块，靠"先想清楚状态转换是否完备，再写代码"和每个算子独立单测（tests/ 下 20+ 个测试文件，覆盖解析器、各执行算子、B+Tree、外键、子查询、优化器）来兜底，比出 bug 后靠猜高效得多。查问题先从日志定位（Logger 贯穿全链路），再写最小复现单测。

**4. 工程意识：诚实面对简化，"先正确后性能"要配 TODO 清单**

这个项目里"正确性优先"留下了几处简化（内存索引、无拆包、恢复未实现、表级锁），它们不是隐藏的缺陷而是**明确的 TODO**——知道简化在哪、为什么简化、怎么补全，和不知道是完全不同的两种状态。复盘、面试时主动讲清边界，比藏着掖着更可信，也让自己清楚下一步往哪走。

**5. 后续方向**：页式存储 + Buffer Pool；BEGIN/COMMIT 接入 SQL 层 + WAL redo 恢复；MVCC + 行级锁提升并发；Hash Join 替代嵌套循环；执行引擎向量化；协议长度字段拆包。
